# 写作与知识维护

## 一章围绕一个明确问题

定义章先固定目标与符号，算法章说明对前一方法做了什么改变，实验章展示实际运行证据。推导中将等式、近似和工程选择区分开。

## 状态随证据推进

| 状态 | 含义 |
| --- | --- |
| 规划 | 只有主题和完成条件 |
| 初稿 | 有可阅读内容，尚未完成原稿核对和技术审阅 |
| 推导已核对 | 与手稿、定义和来源逐步核对 |
| 实验已验证 | 指定配置下实际运行并保留记录 |
| 整理完成 | 必要推导、例子、引用与审阅全部完成 |

理论与代码分别标记进度；个人“已学过”不自动等于项目内容完整。

## 从手稿到知识库

先转写原推导，再统一条件、下标与符号，然后解释关键跳步。补一个可手算的例子，并列出仍然不清楚的问题。每章末尾保留来源和下一步。

对于 GRPO/GSPO，额外注明论文版本、结果监督或过程监督、token 或序列聚合、长度归一化与 KL 项。不同实现不能只因算法名称一致就混合解释。

## 从知识库到文章

知识库保留可检索定义、完整推导与实验配置；公众号文章可以围绕其中一个问题重新组织叙述。文章与写作规划可在独立目录或仓库中维护，并记录其引用的知识库章节，避免同一段内容在两个位置被分别修改而失去对应关系。

仓库根目录的 `CONTRIBUTING.md` 给出完整贡献规范，`templates/` 提供章节、论文阅读与实验记录模板。
